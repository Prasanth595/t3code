# Subpolar integration architecture

## Source baseline

- T3 Code upstream: `e58a4857130a93cc58b45dd6ebee14cf08df04ec` (`upstream/main`, 2026-10-16).
- Subpolar: `2ddbce819d4a364de075f5d2541eeecb37ac00e8` (`automations`, 2026-10-11).
- No root `LICENSE` file was present in the supplied Subpolar checkout; provenance is recorded here and in the migration matrix.
- T3 is the primary repository and pnpm workspace. Subpolar remains an optional server-side runtime.

## Ownership

T3 owns threads, conversation history, orchestration events, provider lifecycle, project worktrees, Git operations, checkpoints, terminals, previews, and client protocol. Subpolar may supply runtime composition, Pi execution, tools, policies, and approvals. A Subpolar runtime session is referenced by a T3 provider session; it does not replace T3's thread or event state.

The first migration increments import the runtime contracts, policy gateway, transient Pi adapter, tool registry, runtime host, ACP bridge, and a backend-neutral environment manager contract under `packages/subpolar-*`. They do not add client UI, RPC methods, event schemas, a new provider kind, or a competing persistence store. T3's native Pi provider remains available. Managed execution must be opt-in and fail closed if its runtime is unavailable.

## Integration boundary

T3's refreshed server uses the `provider-acp` and `provider-acp-registry` packages and orchestration-v2. Its existing ACP registry provider already accepts a local executable path and arguments, so `@subpolar/acp` can use that path without a new provider kind or driver registration. The bridge delegates prompts through `@subpolar/runtime-host`, which composes the Subpolar stateless runtime and Pi adapter. Sessions and transcripts live only in process memory and cannot resume after a restart. When `SUBPOLAR_MANAGER_URL`, `SUBPOLAR_MANAGER_TOKEN`, and `SUBPOLAR_STORAGE_ROOT` are set for the T3 server, the ACP bridge exposes a single argv execution tool through the authenticated environment-manager client; every call requires T3's one-time ACP approval. With those settings unset, the bridge exposes no tools. The execution command runs in the selected worktree's managed environment and fails closed if manager execution is unavailable. The bridge accepts text/resource-link prompts and streams text/tool-call status while retaining the existing ACP contract.

`@subpolar/environments` provides stable owner/workspace/worktree identities, canonical path containment checks, same-process lifecycle request coalescing, an optional local registration store, and an injected backend contract. The local store persists environment metadata with restrictive file permissions and can reconcile registered resources after manager restart. Its Docker adapter accepts a restricted client interface and applies bounded container settings, validates labels/configuration on lifecycle operations, and maps a worktree to a writable bind mount. For linked Git worktrees it can additionally mount only the verified common Git directory when explicit gateway and Docker-host Git roots are configured. The worker mount preserves Git's absolute metadata pointer. The adapter exposes a narrow argv process API that re-verifies the container identity and constrains its working directory to the mounted worktree. A Docker Engine HTTP client implements container lifecycle calls through a Unix socket, and its process runner uses `docker exec -i` to start the packaged worker supervisor. The supervisor streams output and terminates the command's process group on cancellation or stream loss. Both Docker access and the CLI must live in a dedicated manager process, not the T3 gateway; the worker container receives neither the Docker socket nor Docker CLI. The process runner and supervisor have local protocol tests, but no real container execution has been validated. It assumes the operator has configured gateway and Docker-host roots that map to the same underlying storage; path validation cannot prove storage equivalence. T3 has not yet configured these roots or routed execution through this adapter.

The ACP bridge is now a workspace dependency of the T3 server, so an operator can configure it through T3's existing local ACP command setting. For a source checkout, the command can be Bun with `packages/subpolar-acp/src/cli.ts` as its argument. This makes the ACP entry point available without adding a provider kind or changing the client protocol; it does not configure a Subpolar provider automatically. The bridge process and Pi SDK still run on the T3 host; only its approved argv execution tool uses the manager. Runtime sessions cannot yet resume after a restart.

The environment package now exposes an authenticated HTTP handler/server factory and client for lifecycle and streaming process operations. The API is not yet launched as a separately configured manager process, and T3 does not instantiate the client or route execution through it. There is no cross-process registration transaction, Docker container enumeration/orphan cleanup, or environment execution transport into the ACP runtime. The optional JSON registration store is suitable for a single manager process and does not provide a distributed lock. T3 terminals and Git still use server-side host process services. T3 configuration and runtime integration for linked-worktree mounts, container execution, terminal routing, previews, and automated cleanup are still required before managed execution can be enabled. These packages do not claim those capabilities.

## Source disposition

Subpolar's existing frontend and `@subpolar/client` are not imported. Its application backend is not copied wholesale because it combines Bun APIs, PocketBase, profile/session routing, tools, Git, and old UI concerns. Persistence, automations, browser services, and external-agent adapters remain deferred until they can be adapted without duplicating T3-owned state.
