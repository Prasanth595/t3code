## Ownership

T3 owns threads, conversation history, orchestration events, provider lifecycle, project worktrees, Git operations, checkpoints, terminals, previews, and client protocol. Subpolar may supply runtime composition, Pi execution, tools, policies, and approvals. A Subpolar runtime session is referenced by a T3 provider session; it does not replace T3's thread or event state.

The first migration increments import the runtime contracts, policy gateway, transient Pi adapter, tool registry, runtime host, ACP bridge, and a backend-neutral environment manager contract under `packages/subpolar-*`. They do not add client UI, RPC methods, event schemas, a new provider kind, or a competing persistence store. T3's native Pi provider remains available. Managed execution must be opt-in and fail closed if its runtime is unavailable.

This is a partial integration. There is no durable T3-thread-to-Subpolar-session binding or session resume. T3 still owns the thread and event log; the ACP bridge's runtime session is process-local. The ACP `auth/login` method is forwarded as an agent authentication method, but this integration does not broker T3 provider credentials to Pi or workers. The Pi adapter can accept an injected `modelRuntime`, but no server-owned model credential broker is connected to it. The bundled worker image includes the ACP/Pi runtime, but the worker has no provider credentials or model API egress. A real managed Pi turn is therefore not available from the current deployment configuration.

## Integration boundary

T3's refreshed server uses the `provider-acp` and `provider-acp-registry` packages and orchestration-v2. Its existing ACP registry provider accepts a local executable path and arguments, so `@subpolar/acp` uses that path without a new provider kind or driver registration. By default, the bridge delegates prompts through `@subpolar/runtime-host`, which composes the Subpolar stateless runtime and Pi adapter. Sessions and transcripts live only in process memory and cannot resume after a restart. When manager URL, token, and storage root are configured for the T3 server, local mode exposes one argv execution tool through the authenticated environment-manager client; every call requires T3's one-time ACP approval. With those settings unset, local mode exposes no tools. Set `SUBPOLAR_ACP_EXECUTION=managed` to use the authenticated non-TTY process transport instead: the bridge starts one configured worker command for each ACP session, forwards ACP requests, updates, and client callbacks, and returns worker startup failures without falling back to a local runtime. The bundled worker image includes the ACP/Pi runtime. When it runs with the proxy's explicit worker flag, it exposes a workspace-bounded argv execute tool whose permission requests flow back to T3; it inherits no manager token, caps output, and supports cancellation. The worker image receives no T3 state, provider credentials, or Docker socket. A model credential broker and restricted model-network gateway are not implemented, so the packaged runtime cannot complete a real managed Pi turn.

`@subpolar/environments` provides stable owner/workspace/worktree identities, canonical path containment checks, same-process lifecycle request coalescing, an optional local registration store, and an injected backend contract. The local store persists environment metadata with restrictive file permissions and can reconcile registered resources after manager restart. Its Docker adapter accepts a restricted client interface and applies bounded container settings, validates labels/configuration on lifecycle operations, and maps a worktree to a writable bind mount. For linked Git worktrees it can additionally mount only the verified common Git directory when explicit gateway and Docker-host Git roots are configured. The worker mount preserves Git's absolute metadata pointer. The adapter exposes a narrow argv process API that re-verifies the container identity and constrains its working directory to the mounted worktree. A Docker Engine HTTP client implements container lifecycle calls through a Unix socket, and its process runner uses `docker exec -i` to start the packaged worker supervisor. The supervisor streams output and terminates the command's process group on cancellation or stream loss. Both Docker access and the CLI must live in a dedicated manager process, not the T3 gateway; the worker container receives neither the Docker socket nor Docker CLI. The process runner and supervisor have local protocol tests, but no real container execution has been validated. Compose supplies configurable gateway and Docker-host storage roots; those paths must resolve to the same underlying workspace data, which path validation cannot prove. No real managed provider flow has yet been validated against a running Docker daemon.

The ACP bridge is now a workspace dependency of the T3 server, so an operator can configure it through T3's existing local ACP command setting. For a source checkout, the command can be Bun with `packages/subpolar-acp/src/cli.ts` as its argument. This makes the ACP entry point available without adding a provider kind or changing the client protocol; it does not configure a Subpolar provider automatically. The bridge process and Pi SDK still run on the T3 host; only its approved argv execution tool uses the manager. Runtime sessions cannot yet resume after a restart.

The environment package exposes an authenticated HTTP handler/server factory and client, plus a `subpolar-manager` CLI entry point that composes the Docker Engine client, Docker backend, local registration store, and manager API. The production Compose file has an opt-in `subpolar` profile for this manager; the operator must configure the Docker-host workspace path and build the worker image before enabling it. T3 can route approved ACP argv tools through the authenticated manager client. T3's existing terminal manager can also route terminals for provider instance IDs listed in `SUBPOLAR_MANAGED_PROVIDER_INSTANCE_IDS`; worker PIDs remain private and manager failure is fail-closed. The managed terminal transport uses the same worktree mount and preserves the existing terminal wire protocol.


In local mode the ACP bridge and Pi runtime execute in the T3 gateway process, while only its approved argv tool runs in the worker. Managed mode runs the ACP/Pi runtime inside the worker, but cannot access a model provider because credentials and model egress are not wired. T3 Git operations still run on the gateway. Preview discovery and forwarding from worker containers are not implemented. There is no cross-process registration transaction, Docker container enumeration/orphan cleanup, or distributed lock; the optional JSON registration store is suitable for a single manager process. No real Docker execution or integrated T3-client flow has been validated. The terminal adapter is available only when explicitly configured and must not be described as complete managed agent isolation.

The Docker backend now discovers image-based Dev Container configurations at the worktree root and `.devcontainer/`, including named configs. A single config is selected automatically; when multiple configs exist the operator must choose with `SUBPOLAR_DEFAULT_DEVCONTAINER_CONFIG`. It uses the configured image while retaining the manager's isolation policy, and rejects unsupported options rather than ignoring them. Dockerfile builds, Features, Compose, lifecycle hooks, custom mounts, environment overrides, and port forwarding remain unsupported; see [Dev Container support](dev-containers.md).

The manager exposes authenticated non-TTY process sessions with stdin forwarding, sequenced stdout/stderr events, reconnectable output, and process-group termination. The managed ACP proxy uses this transport. The bundled worker image includes the Subpolar ACP bridge and Pi SDK; its build has not been verified because Docker is unavailable on this host.

## Current verified state

The current tree contains the seven package directories listed in [the migration matrix](migration-matrix.md). Focused Bun tests have passed for the Pi adapter, runtime host, managed ACP proxy, and worker execution. A broader ACP package run had 27 passing tests but could not load `agent.test.ts` because Bun could not import Vitest-only `assert` from `@effect/vitest`. Frozen pnpm lockfile validation succeeded across all 40 workspace projects. Typechecking was unavailable because the filtered install lacked platform-specific `tsc-rs` and TypeScript 7 packages; the Vite+ native test runner was also unavailable. No Docker daemon was available, and no integrated T3-client, real Pi turn, or container execution has been verified. See [upstream compatibility](upstream-compatibility.md) for the validation boundary and remaining work.

## Source disposition

Subpolar's existing frontend and `@subpolar/client` are not imported. Its application backend is not copied wholesale because it combines Bun APIs, PocketBase, profile/session routing, tools, Git, and old UI concerns. Persistence, automations, browser services, and external-agent adapters remain deferred until they can be adapted without duplicating T3-owned state.
